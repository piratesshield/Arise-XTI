1. Architecture Overview

ARISE is a state-driven EASM toolkit that converts a list of target domains into a complete exposure map. The system has three layers:

Target domains

→

→
manifest.json
State Store
→
dashboard.py
Flask Dashboard

Data Flow

  1. arise.py reads hosts.txt, creates a timestamped scan directory under scans/, launches the pipeline
  2. easm-pipeline.sh runs 18 modules sequentially, writing results to numbered subdirectories and updating manifest.json
  3. dashboard.py reads scan directories, parses all data sources (manifest, nuclei JSON, nmap services, httpx tech, cloud findings), and serves a real-time dashboard on port 5000
  4. Each scan is isolated: scans/{domain}-{DDMMYY}-{HHMM}/ with its own manifest, logs, and module output folders

5. Cloud Exposure Detection

Module 17 is cloud-only. It runs in three phases and scores each finding with a weighted model. App/API vulnerabilities (XSS, SQLi, SSRF, IDOR, JWT) never appear on the Cloud dashboard — a category whitelist keeps them in the Vulns/API tabs.

weighted_score = base_weight × exploitability × exposure

Three-phase pipeline

PhaseWhatToolsAuth
1. DetectionMisconfiguration scanning + origin-bypass + leaked creds + email posturenuclei + custom cloud-templates, dig, trufflehogNone (external)
2. Storage reconEnumerate S3/GCS/Azure buckets from the target keyword, then check anonymous access + list objectscloud_enum → s3scannerNone (external)
3. Compliance auditAccount-wide CIS/PCI/HIPAA checks against the cloud APIsprowler or scoutsuiteRequires cloud credentials — OFF by default

Why Phase 3 is gated: Prowler/ScoutSuite scan a cloud account from the inside via authenticated APIs. In an external scan you don't have the target's credentials, so Phase 3 stays off unless the operator sets CLOUD_AUDIT_ENABLED=true and supplies credentials (auditing your own estate, or authorized post-compromise).

Cloud dashboard layout

  • Recon & estate inventory — cloud providers per host (from httpx tech), CDN/edge fronting, exposed origin IPs (direct, not behind CDN), enumerated storage buckets
  • Security findings — scored misconfigurations, grouped into security (public storage, K8s, metadata, Terraform state, CI/CD, datastores, origin bypass, debug) and posture (missing WAF, missing SPF/DKIM/DMARC)
  • Compliance audit — hidden unless Phase 3 ran; shows failed CIS/PCI checks by service

6. API Security Testing

API Intelligence Engine (owns auth/authz + black-box)

  • Deterministic, no OpenAPI spec required — probes and classifies every discovered URL (crawl, JS, dirsearch, Module 20 XHR interception).
  • Bundles apisec.py (stdlib black-box scanner) as its verification engine; findings are response-gated to keep false positives low.
  • Autoswagger (auth/authz) and RESTler (robustness) were removed. Autoswagger needed a published spec and duplicated the intel engine's auth/authz findings at a higher false-positive rate; RESTler produced ~1 low-value finding per scan. The intel engine + apisec.py now own the entire API surface.

6b. Extended Verification (Module 19)

Dedicated FOSS scanners confirm vulnerability classes nuclei structurally can't reach. The module is production-safe by contract: it confirms findings, it never exploits them.

Safe-mode contract (EXTENDED_SAFE_MODE=true)

  • No shells, no data exfiltration, no auth-bypass actions, no state mutation
  • GET / read-only requests, benign payloads, rate-limited, URL-capped
  • Confirmation comes from OOB callbacks, response reflection, or offline analysis — never weaponization

Per-check verification method

CheckToolHow it confirms (safely)Confidence
Blind SSRFinteractshInjects an OOB URL into SSRF-sink params; a DNS/HTTP callback proves the server made an outbound request. Nothing internal is read.Confirmed
CRLFcrlfuzzDetects CR/LF reflected into response headers. No XSS/cache-poison chaining.Confirmed
JWTjwt_tool100% offline. Tokens harvested from responses/JS are decoded and cracked locally against a wordlist. Zero requests sent — no auth bypass possible.Confirmed
SSTISSTImapArithmetic marker payloads ({{7*7}}) identify a vulnerable engine. Never --os-shell/-X.Probable
GraphQLgraphw00fRead-only engine fingerprint + introspection state on discovered /graphql endpoints.Informational
HTTP smugglingsmugglerGated off by default. Desync probes can disturb other users' production traffic — opt-in via CHECK_SMUGGLING=true.Probable

Findings land in the Vulns tab with source Extended Verification and a confidence badge (Confirmed / Probable / Info). Output: 19_extended_checks/extended_findings.jsonl.

6c. ARISE Correlation Engine (Phases 0-4)

ARISE's correlation engine is the multi-phase entity and issue correlation system that transforms raw pipeline findings into correlated, lifecycle-managed security issues.

Phase 0: Entity Index Engine (kaiju_entities.py)

Invariant INV-1: Stable, deterministic entity references derived from natural keys.

  • 7 Entity Types: domain, subdomain, host (keyed on IP), service, technology, vulnerability, certificate
  • Entity Refs: SHA1(natural_key)[:10] — deterministic, byte-identical on recompute
  • Relations: 6 types — HAS_SUB, RESOLVES_TO, RUNS, USES, AFFECTS, and implicit entity-to-entity links
  • Provenance: Each entity tracks which scanner(s) produced it (nuclei, nmap, trufflehog, etc.)
  • Graph Traversal: N-hop related-entity lookup for the entity drawer's Related tab
  • Storage: scans/<id>/.derived/entities.json (regenerable, safe to delete)

Phase 1: Entity Drawer (Global UI Component)

  • Right slide-over panel — 480px (min 92vw on mobile), opens from any entity reference in the app
  • 4 Tabs per entity:
    • Summary — all entity attributes as key/value pairs
    • Related — 1-hop graph neighbors grouped by type, clickable to open their drawer (stack navigation)
    • Issues — all issues affecting this entity
    • Raw — provenance, ref string (monospace), full JSON dump
  • Keyboard: Esc closes, focus trapped while open
  • Integrated into: Issue evidence chains, timeline events, related-entity navigation

Phase 2: Issues Lens (Deep-Linked Landing Page)

  • Default landing view — issues as primary investigative surface
  • Severity filters — clickable chips (Critical, High, Medium, Low) with counts, multi-select capable
  • Status filter — dropdown (All / Open / Acknowledged / Resolved / False positive / Accepted risk)
  • Sortable by: Risk descending, Severity, Newest
  • Issue rows: gradient card with severity stripe, title, status pill, ref, rule name, detection count, risk score
  • Click to drawer — opens Issue detail panel

Phase 3: Issue Lifecycle & Correlation Rules

Invariant INV-2: Human-set statuses (false_positive, accepted_risk) survive recompute.

  • 8 Correlation Rules (all validated against real data):
    1. exposed-service — sensitive DB/cache ports (3306, 5432, 6379, 27017, etc.) exposed to internet
    2. dev-staging-exposed — dev/staging/test subdomains resolving to public IPs
    3. missing-headers — web apps missing critical security headers (HSTS, CSP, X-Content-Type-Options)
    4. leaked-secret — API keys/credentials found by TruffleHog in JS files
    5. hsts-gap — HSTS misconfiguration (missing HTTP→HTTPS redirect, missing/weak header, no preload) from the dedicated 5-test HSTS audit (tls/hsts_audit.py); catches the no-redirect MITM case that missing-headers can't (it only fires when 2+ of 6 headers are missing)
    6. new-asset — subdomains appearing for the first time vs. previous scan
    7. no-waf — web applications without WAF protection
    8. compounding-risk — the first rule to actually walk the RUNS/RESOLVES_TO/AFFECTS relations for risk computation (not just cosmetic labels): fires when 2+ independent risk factors (exposed sensitive service, confirmed high/critical vuln, no WAF, weak headers) converge on the SAME host, since combined exploitability is materially higher than any one factor alone (e.g. a web vuln becomes a pivot to an exposed DB on the same box)
  • Issue Lifecycle:
    1. Computed issues matched against issues-state.json by ref
    2. New issues → status=open, detections=1, created event
    3. Re-detected issues → detections+=1, last_seen_rev updated
    4. Open issues not in computed set → status=resolved, auto_resolved event
    5. Human-set statuses NEVER auto-resolved (INV-2)
    6. Orphaned entries (rule removed) → tombstoned with orphaned_at, reattach on recompute
  • Atomic writes: Temp file → os.rename() → .bak backup
  • Issue detail drawer: Evidence chain (clickable refs), "Why flagged" (markdown), status change form (requires note for false_positive/accepted_risk), remediation, history

Phase 4: Timeline & Event Stream

  • Append-only event log — state/<target>/events.jsonl (retention-exempt, Drive-synced first)
  • 11 Event kinds: new_subdomain, subdomain_gone, new_ip, ip_gone, port_opened, port_closed, service_changed, new_vuln_match, issue_created, issue_auto_resolved, issue_reopened, issue_status_changed
  • Diff summary strip — chips counting events by kind at top of timeline view
  • Event rows: kind icon (colored), description with clickable entity labels, revision tag
  • Idempotent append: Re-running correlate never duplicates events (verified by test)
  • Timeline nav item added to sidebar (between Graph and AI)

On-Disk Layout (ARISE Correlation State)
